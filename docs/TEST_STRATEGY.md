# TEST_STRATEGY.md

## テスト方針

- 【要記入】バックエンド・フロントエンドそれぞれで書くテストの種類
- 重要なビジネスロジック・権限チェックは必ずテストを書く

## バックエンド

### テストツール

- 【要記入】例: pytest / JUnit / Jest
- テストファイルの配置: 【要記入】

### テスト実行

```bash
# 【要記入】
<command>
```

### テストの種類と対象

| 種類 | 対象 | 例 |
|---|---|---|
| ユニットテスト | モデルのメソッド・バリデーション・純粋関数 | 【要記入】 |
| 統合テスト（APIテスト） | ViewとDBを含むAPIの動作 | 【要記入】 |

### テストで必ずカバーすること

- 【要記入】コア機能の正常系（`REQUIREMENTS.md` のIDと紐づけると良い）
- 権限のないユーザが操作した場合に `403` が返ること
- 他組織のデータにアクセスできないこと（データ分離）
- 外部依存（外部API・メール等）が失敗しても主要機能が壊れないこと

### モック方針

- 外部サービス（メール送信・外部APIなど）はモックする
- DBはテスト用DBを使用し、モックしない

## フロントエンド

### テストツール

- 【要記入】例: Playwright / Vitest / Testing Library
- テストファイルの配置: 【要記入】

### テスト実行

```bash
# 【要記入】
<command>
```

### テストで必ずカバーすること

- 【要記入】主要画面の表示・操作フロー
- 入力バリデーションエラーの表示
- APIエラー・通信エラー時の表示

### フロントエンド変更時のテスト修正ルール

- 新しいページを追加した場合: 対応するテストを新規作成する（正常系・異常系・権限）
- 既存UIを変更した場合: 対応する既存テストを修正し、新しい操作フローにはテストを追加する
- 共有コンポーネント・共有モックを変更した場合: 全テストが通ることを確認する

### APIモック方針

- バックエンドを起動せずテストできるよう、API呼び出しをモックする（【要記入】手段）
- テストデータは固定値で定義し、ランダム性を排除する
- モック登録は各テストの前処理で行い、テスト間の状態汚染を防ぐ

## テストデータ

- フィクスチャ機能でテストデータを管理する
- テスト専用のシードデータはテストコードに直接記述し、外部ファイルへの依存を最小化する

## 脅威モデルの概要

【要記入】システムが扱うアクター（認証ユーザ・未認証ユーザ・管理者など）と、主な脅威を書く。
典型的な脅威: 他組織のデータ参照、認証回避、インジェクション攻撃、機密情報の漏洩。

## 認証・認可

### 認証方式

- 【要記入】例: JWT Bearer / セッションCookie / OAuth
- トークン有効期限: 【要記入】
- 認証方式を選んだ理由は `docs/adr/` に記録する

### 認証が不要なエンドポイント

| エンドポイント | 理由 |
|---|---|
| 【要記入】`GET /api/health/` | ヘルスチェック |

上記以外のAPIエンドポイントは**すべて認証必須**とする。

### 【要確認: マルチテナントの場合】組織（テナント）レベルの権限チェック

ユーザは自身が所属する組織のデータのみ参照・操作できる。
**他組織のデータへのアクセスは絶対に許可しない。**

```python
# 例（Django）
# ✅ 所属組織でフィルタリング
def get_queryset(self):
    return Project.objects.filter(account=self.request.user.account)

# ❌ 危険: 全件返してしまう
def get_queryset(self):
    return Project.objects.all()
```

### リソースレベルの権限チェック

【要記入】ロールごとに操作可能な範囲を定義し、チェックを共通関数に集約する。

## インジェクション対策

### SQLインジェクション

- **ORMを必ず使用する**。生SQLは原則禁止。
- やむを得ず生SQLを使う場合はパラメータバインドを使う。

### XSS（クロスサイトスクリプティング）

- フロントエンドのフレームワークのデフォルトエスケープを活用する。
- HTMLを直接挿入するAPI（例: `dangerouslySetInnerHTML`）の使用を禁止する。
- URLを動的に組み立てる場合はエンコードする（例: `encodeURIComponent()`）。

---

## シークレット管理

- パスワード・APIキー・シークレットキーはコードにハードコードしない。
- `.env` ファイルで管理し、`.gitignore` に含める。
- 本番のシークレットは【要記入】（例: クラウドのシークレット管理サービス）で管理する。

### コミット禁止ファイル

- `.env`（全環境）
- `*.pem`, `*.key`（証明書・秘密鍵）
- 【要記入】その他（例: ライセンス制限のあるデータファイル）

## 【要確認: マルチテナントの場合】データ分離の原則

**異なる組織のデータが混在することは絶対に許可しない。**

すべてのAPIで以下を守る:

1. ログインユーザの所属組織を取得し、クエリのフィルタに必ず含める
2. URLパラメータのIDでオブジェクトを取得する際も、組織フィルタを同時にかけて取得する

```python
# 例（Django）
# ✅ 組織フィルタを含めて取得
project = get_object_or_404(Project, pk=pk, account=request.user.account)

# ❌ pk だけで取得（他組織のデータが返る可能性）
project = get_object_or_404(Project, pk=pk)
```

## 【要確認: パスワード認証の場合】パスワード

- フレームワーク標準の安全なハッシュを使用する。
- パスワードをプレーンテキストでログに出力しない。
- パスワードリセットはメール経由のトークンフローで行う。

## ロギングとモニタリング

- ログにパスワード・トークン・個人情報を含めない。
- `print()` ではなくロギングライブラリを使う。
